## 三、面试官可能问的问题及回答

### 问题1：什么是贫血模型？有什么问题？

**回答逐字稿**：
```
贫血模型是指实体类只有字段和getter/setter，没有任何业务行为，所有的业务逻辑都写在Service层。

主要问题有三个：
第一，实体只是数据容器，无法体现业务语义。比如Task实体不知道自己是否有效，需要Service来判断。
第二，业务逻辑散落在各处，同样的判定逻辑可能在多个Service里重复写。
第三，跨项目协作困难，其他业务方如果要使用Task，需要自己实现判定逻辑。

我们原来的系统就是典型的贫血模型，导致每次新任务上线都要业务方写代码，周期很长。
```

**可能追问**：充血模型具体怎么设计的？能举个例子吗？

**追问回答**：
```
比如Task实体，我给它加了几个方法：
- isValid()：判断任务是否在有效期内
- matchesUserTags()：判断用户是否符合投放标签
- isInExperimentGroup()：判断用户是否在实验组

这样Task实体自己就具备了完整的业务行为能力，Service层只需要调用这些方法，不需要关心具体怎么判断。

再比如Behavior实体，它有matchesEvent()方法，可以判断一个埋点事件是否匹配这个行为定义。这样行为匹配的逻辑也封装在实体里了。
```

---

### 问题2：SDK是怎么设计的？如何保证配置热更新？

**回答逐字稿**：
```
SDK主要包含四个核心功能模块：

第一是配置拉取模块，SDK启动时会从服务端拉取当前生效的行为配置列表，并且每分钟定时刷新，保证配置是最新的。

第二是事件监听模块，业务方调用trackEvent()上报埋点事件，SDK会匹配本地缓存的行为配置。

第三是过滤去重模块，防止重复计算。我设计了去重Key策略，比如"用户ID:事件名:日期"，同一天同一事件只算一次。

第四是上报模块，匹配到行为后，SDK会调用服务端接口通知任务系统进行判定。

热更新是通过定时刷新配置实现的，SDK内部用CopyOnWriteArrayList存储配置，刷新时直接替换整个列表，保证线程安全。
```

**可能追问**：如果服务端挂了，SDK怎么处理？

**追问回答**：
```
实际项目中应该考虑降级策略。比如：
- SDK本地缓存配置，服务端不可用时使用缓存配置
- 上报失败时本地队列暂存，恢复后重试
- 设置超时和熔断，避免影响主业务流程

我在实习期间主要完成了核心功能，这些容错机制是后续迭代计划中的内容。
```

### 问题3：表达式引擎是怎么用的？为什么选Aviator？

**回答逐字稿**：
```
选Aviator主要有三个原因：
- 轻量级，核心只有70K
- 高性能，直接编译成Java字节码执行
- 功能丰富，支持函数、变量、运算符

主要用在三个场景：
第一是数据预处理过滤，比如"originEvent.pay_status == 1 && originEvent.amount > 100"
第二是规则计算，判断行为是否达成
第三是动态奖励计算，比如"event.amount / 100"，消费100元返1积分

实现上我定义了ExpressionEngine接口，然后有AviatorExpressionEngine实现类。RuleEngine基于这个接口进行规则计算，这样以后如果要换表达式引擎也很方便。
```

**可能追问**：表达式引擎有什么安全风险吗？

**追问回答**：
```
有的，主要风险是表达式注入和无限循环。

安全措施包括：
- 表达式需要预先审核，不能让用户随意输入
- 设置执行超时，防止死循环
- 限制表达式复杂度，比如最多100个字符
- Aviator本身支持设置最大循环次数

我在项目中做了基本的表达式验证，更完善的安全策略是后续可以优化的方向。
```

### 问题4：多源数据采集怎么设计的？

**回答逐字稿**：
```
我定义了DataSourceType枚举，支持四种数据源：
- TRACKING：埋点数据，通过SDK采集
- DATABASE：数据库，比如从订单表采集
- MESSAGE_QUEUE：消息队列，消费订单完成事件
- API：外部API接口

每种数据源有对应的DataSourceConfig配置，包含连接信息、预处理表达式、字段映射等。

数据进入系统后，先经过预处理层，用Aviator表达式过滤。然后通过归一化层，把不同格式的数据映射成统一格式。最后进入规则计算层。

这样设计的好处是扩展性强，新增数据源只需要添加配置，不需要改核心代码。
```

**可能追问**：数据一致性怎么保证？

**追问回答**：
```
不同数据源有不同的保证策略：

对于埋点数据，SDK端有去重机制，服务端也有幂等校验。

对于MQ数据，依赖MQ的至少一次投递，服务端消费时做幂等处理，用"用户ID+事件ID"作为唯一键。

对于数据库，采用定时轮询+增量同步，记录上次同步的时间戳。

整个系统设计上是无状态的，支持水平扩展，可以通过增加实例来提升处理能力。
```

### 问题5：这个项目最大的挑战是什么？

**回答逐字稿**：
```
最大的挑战是架构重构的兼容性。

因为系统已经在运行，不能停服务重构。我需要保证：
- 新系统能兼容老数据
- 新老系统可以并行运行
- 逐步迁移，风险可控

我的做法是采用阶段式演进：
- 阶段一：保留原有接口，内部实现逐步替换
- 阶段二：新功能走新架构，老功能逐步迁移
- 阶段三：完全切换到新架构，下线老代码

另一个挑战是表达式引擎的调试。运营同学配置表达式后，如果执行结果不对，需要有调试工具。我设计了日志记录机制，记录每个表达式的执行过程和结果，方便排查问题。
```

### 问题7：DDD领域驱动设计你是怎么理解的？

**回答逐字稿**：
```
DDD的核心思想是让代码结构反映业务领域。

我理解的几个关键点：

第一是充血模型，实体不仅有数据，还有行为。比如Task实体知道怎么验证自己，而不是靠Service来验证。

第二是限界上下文，明确系统的边界。积分任务系统只关注任务生命周期，用户积分账户是另一个上下文，通过接口交互。

第三是统一语言，开发、产品、运营用同一套术语沟通。比如"行为"、"任务"、"达成"这些概念所有人理解一致。

第四是防腐层，外部系统的变化不影响核心领域。比如数据源的变化通过适配器隔离，不影响任务计算逻辑。

这个项目让我对DDD有了实践层面的理解，特别是充血模型的优势体会很深。
```
