### **1. 原系统的问题（架构痛点）**

#### **阶段一的痛点**：
- **跨项目协作周期长**：
  - 跨项目管理难度大
  - 进度对齐、沟通协调困难
  - Case by case开发，系统耦合严重
  - 灵活性低，业务方逻辑重、开发成本高

- **业务上运营效率低**：
  - 一个季度上线不了几个任务
  - 加上数据分析周期，整体跨度长
  - 效果不理想
  - 虽然任务基础信息可通过配置化完成，但远没有达到预期的"通过配置化就能够实现任务快速上线"

#### **阶段二的痛点**：
- **行为采集源单一**：非埋点行为类的任务不支持
- **触达形式单调**：只支持简单的toast以及snackbar

---

### **2. 思考逻辑（思考过程）**

#### **问题分析**：
1. 初始系统仅引入了任务的定义与配置，但任务的行为以及达成判定都由业务方实现
2. 发现大多数任务行为都是app端侧产生的行为（如用户浏览新闻）
3. 结合互联网业务都有日常埋点的现状，可以利用埋点上报捕获用户行为
4. 识别到需要支持的核心功能点：
   - 引入行为模型
   - 建设行为SDK
   - 支持实验能力

#### **业务本质分析**：
- 任务的本质是"收集行为、判定任务关联行为是否达成、任务的奖励发放、对用户的触达"
- 需要着重关注：
  - 行为采集源的拓展
  - 支持复杂行为计算
  - 动态的规则配置

---

### **3. 核心的演化逻辑（要改动的东西）**

#### **阶段一 → 阶段二的演化**：

**从被动配置到主动采集**

| 维度 | 阶段一 | 阶段二 |
|------|------|------|
| **采集方式** | 业务方主动接入实现 | SDK主动采集埋点 |
| **判定逻辑** | 业务方实现 | 系统处理 |
| **集成成本** | 每次接入都需开发 | 一次接入，后续零成本 |
| **上线周期** | 1-3个月 | 1-3人天 |
| **支持能力** | 基础的配置 | 基础+实验+标签投放 |

#### **阶段二 → 阶段三的演化**：

**从单一埋点到多源采集 + 灵活计算**

| 维度 | 阶段二 | 阶段三 |
|------|------|------|
| **数据源** | 仅支持埋点 | 埋点、数据库、消息队列、API/RPC |
| **规则配置** | 固定规则 | 动态表达式 |
| **触达形式** | Toast/Snackbar | 自定义弹窗 + 消息透传 |
| **计算能力** | 简单判定 | 复杂行为计算（如根据金额分级奖励） |

### **5. 系统架构三个阶段的完整演进**

#### **阶段一：初探（基础任务系统）**
```
业务方 
  ↓
端侧（App + SDK）
  ↓
任务服务
```
- 特点：业务方直接实现任务逻辑
- 局限：耦合紧密，成本高

#### **阶段二：用户行为激励体系建设**
```
端侧App
  ↓
行为SDK（拉取配置、上报行为、过滤、去重）
  ↓
行为上报服务（用户标签、实验策略、行为计算）
  ↓
任务服务
  ↓
用户（Toast/Snackbar提示）
```
- 特点：SDK采集埋点，系统统一处理
- 优势：降低业务方成本，加快上线速度

#### **阶段三：扩大行为采集源，丰富触达形式**

**多源数据采集**：
```
┌─────────────────────────────────────┐
│ 数据源                               │
├──────────┬──────────┬──────┬──────┐
│ 埋点数据 │ 数据库   │ 消息队列│API  │
│ (SDK)    │ (MySQL)  │(MQ)  │(RPC) │
└──────────┴──────────┴──────┴──────┘
          ↓
    采集层（数据预处理）
    ├─ 集群管理
    ├─ 数据源管理
    ├─ 元数据管理
    ├─ 数据预处理（Aviator过滤）
    ├─ 数据归一化
    └─ 数据存储(MongoDB/TiDB)
          ↓
    规则计算层（表达式引擎）
    └─ 支持复杂行为计算
          ↓
    任务层
    ├─ 任务与行为关联
    ├─ 任务投放
    ├─ 奖励发放
    └─ 用户状态管理
          ↓
    触达层
    ├─ 自定义弹窗
    └─ 消息透传
```

### **6. 核心技术选型**

1. **表达式引擎**：选择 **AviatorScript**
   - 轻量级：仅70K（不含依赖）
   - 高性能：直接编译为Java字节码
   - 灵活性：支持复杂业务逻辑动态配置

2. **数据存储**：
   - 初选：Elasticsearch（后弃用）
   - 最终：MongoDB + TiDB（满足聚合计算需求）

3. **消息中间件**：RocketMQ/Kafka

4. **规则引擎**：Aviator表达式引擎
