## 各实践详细解读

### 1. DDD充血模型

**详细解释：**
贫血模型中Entity只有getter/setter，业务逻辑散落在Service层。充血模型将业务行为封装到Entity中，实体自己知道如何验证自己、如何计算。例如Task实体包含isValid()、calculateReward()等方法，符合面向对象设计原则。

**通俗解释：**
就像一个人（Entity），贫血模型只让他有姓名、年龄属性（getter/setter），所有行为（走路、吃饭）都要别人（Service）来指挥。充血模型是让这个人自己知道怎么走路、怎么吃饭，更自然、更内聚。

**实际案例：**
```java
// 贫血模型：到处散落校验逻辑
public class TaskService {
    public void createTask(TaskDTO dto) {
        if (dto.getStartTime() == null) throw new Exception();
        if (dto.getEndTime().before(dto.getStartTime())) throw new Exception();
        if (dto.getReward() <= 0) throw new Exception();
        // ... 20行校验代码
    }
}

// 充血模型：实体自己校验
public class Task {
    public boolean isValid() {
        return startTime != null 
            && endTime.after(startTime) 
            && reward > 0;
    }
}
```

### 2. 三表分离架构

**详细解释：**
将积分数据拆分为总额表（UserPointWallet）、流水表（PointFlowLog）、明细分桶表（PointDetailBucket）。总额表提供快速查询，流水表记录审计日志，明细表支持过期管理和FIFO扣减。三者互相校验保证数据一致性。

**通俗解释：**
就像你的银行卡：
- 总额表 = 银行APP显示的余额（快速查看）
- 流水表 = 银行短信通知（每笔变动记录）
- 明细表 = 每笔存款的到期时间（定期存款明细）

**实际案例：**
```
用户查询积分：查总额表（1ms）
用户查看明细：查流水表（按时间排序）
用户消费积分：查明细表（按过期时间扣减）

三者对账：
总额表余额 = 明细表汇总 = 流水表累计
如果不等，说明数据有问题！
```

### 3. 乐观锁版本控制

**详细解释：**
在数据表中增加version字段，更新时检查version是否变化。如果version没变，更新成功且version+1；如果version变了，说明数据被其他事务修改过，需要重试。适用于读多写少的场景，避免悲观锁的阻塞等待。

**通俗解释：**
就像你去图书馆借书：
- 悲观锁：把书锁在柜子里，你来之前别人都不能看（阻塞）
- 乐观锁：书放在架子上，你借的时候检查一下"还是那本吗？"，是就借走，不是就重新找

**实际案例：**
```sql
-- 查询时获取版本号
SELECT total_balance, version FROM user_point_wallet WHERE user_id = 100;
-- 返回：total_balance=100, version=5

-- 更新时检查版本号
UPDATE user_point_wallet 
SET total_balance = 90, version = 6 
WHERE user_id = 100 AND version = 5;

-- 如果version已经被别人改成6了，这条UPDATE会失败（影响行数为0）
-- 程序捕获失败，重试：重新查询、重新扣减
```

### 4. FIFO扣减机制

**详细解释：**
First In First Out，先进先出。消费积分时优先扣除快过期的积分。实现方式是按expire_time升序查询PointDetailBucket，依次扣减直到满足消费金额。符合"对用户最有利"的法律要求。

**通俗解释：**
就像你冰箱里有很多牛奶：
- 1号牛奶：3天后过期
- 2号牛奶：7天后过期
- 3号牛奶：15天后过期

你要喝一瓶，应该拿哪瓶？当然是拿1号（快过期的）！FIFO就是这个逻辑。

**实际案例：**
```
用户有3笔积分：
- Bucket 1: 100积分，2024-03-01过期
- Bucket 2: 200积分，2024-06-01过期
- Bucket 3: 100积分，2024-12-01过期

用户消费150积分：
1. 先扣Bucket 1的100积分（快过期）
2. 再扣Bucket 2的50积分
3. Bucket 2还剩150积分，Bucket 3不动

结果：用户损失最小化，快过期的先用掉
```

### 5. 规则引擎

**详细解释：**
使用AviatorScript等表达式引擎，将业务规则配置化。运营人员可以通过界面配置任务规则（如"连续签到7天奖励100积分"），无需开发人员修改代码。支持动态热更新，规则变更实时生效。

**通俗解释：**
就像商场的促销活动：
- 没有规则引擎：每换一个活动都要程序员改代码、发版本（1-3天）
- 有规则引擎：运营自己在后台配置"满100减20"，立刻生效（1分钟）

**实际案例：**
```java
// 硬编码方式（没有规则引擎）
if (user.getSignInDays() >= 7) {
    giveReward(user, 100);
}

// 规则引擎方式
String rule = "user.signInDays >= 7 ? 100 : 0";
// 运营在后台修改rule为"user.signInDays >= 3 ? 50 : 0"
// 无需发版，立刻生效
```

### 6. 定期合并（Compaction）

**详细解释：**
后台定时任务扫描用户的PointDetailBucket，将同一用户、相同或相近过期时间的多个Bucket合并成一个。减少Bucket数量，降低消费时需要Update的行数，从而减少锁冲突和死锁概率。

**通俗解释：**
就像你的零钱罐里有很多硬币：
- 合并前：100个1元硬币（数起来麻烦，花起来也麻烦）
- 合并后：1张100元纸币（方便管理）

**实际案例：**
```
用户连续签到30天，每天获得10积分：
- 合并前：30个Bucket，每个10积分
- 消费100积分需要Update 10个Bucket

定期合并后（按周合并）：
- 合并后：4个Bucket（第1周40分、第2周40分、第3周20分、第4周10分）
- 消费100积分只需要Update 3个Bucket

死锁概率大幅降低！
```

### 7. T+1离线提醒

**详细解释：**
T+1表示"今天计算昨天的数据"。每天凌晨用Hive/Spark等大数据工具计算未来N天即将过期的用户清单，然后通过MQ异步发送提醒。避免实时扫全表导致的性能问题，支撑亿级用户规模。

**通俗解释：**
就像学校发成绩单：
- 实时方案：老师每考完一科就立即发成绩（老师累死了）
- T+1方案：每天放学后统一发当天的成绩（批量处理，效率高）

**实际案例：**
```
用户量：5000万
实时扫表：SELECT * FROM bucket WHERE expire_time = '2024-03-01'
- 需要扫描几亿行数据
- 数据库CPU 100%，其他查询都卡住
- 系统崩溃

T+1离线计算：
- 凌晨2点用Hive跑SQL（不影响线上）
- 计算出明天过期的100万用户
- 放到MQ里慢慢发（控制5000 QPS）
- 系统稳稳的
```

### 8. 三重校验机制

**详细解释：**
数据迁移时，同时对比三个数据源的一致性：明细实验表vs明细对照表、新总值表vs老总值表、新总值表vs新明细汇总。任意不一致触发告警并自动修复，确保迁移后数据100%一致。

**通俗解释：**
就像你搬家时清点物品：
- 第一重：新房里的物品清单 vs 旧房里的物品清单
- 第二重：新房的总重量 vs 旧房的总重量
- 第三重：新房的总重量 vs 新房里所有物品重量之和

三重都对了，才放心！

**实际案例：**
```
从MySQL迁移到MongoDB：

第一重：明细对比
- MySQL明细总数：1000000条
- MongoDB明细总数：999999条
- 结果：少了1条！告警！

第二重：总值对比
- MySQL总值：50000000分
- MongoDB总值：50000000分
- 结果：总值一样（但明细少了1条，说明有脏数据）

第三重：汇总对比
- MongoDB总值：50000000分
- MongoDB明细汇总：49999950分
- 结果：差了50分！数据不一致！

自动修复：找出那1条缺失的明细，重新同步
```

### 9. 灰度切流机制

**详细解释：**
系统升级时，按用户ID尾号分批切换流量。第一批1%（尾号00），观察没问题后扩大到10%（尾号00-09），逐步推进到100%。每批都观察核心指标，发现问题立即回滚到上一批次。

**通俗解释：**
就像新药上市：
- 先在100个人身上试验（1%）
- 没问题再在1000个人身上试验（10%）
- 逐步扩大到所有人（100%）
- 如果某批出问题，立即停止，前面的人没事

**实际案例：**
```
系统从V1升级到V2：

第1批（1%）：尾号00的用户用V2
- 观察1天，无异常

第2批（10%）：尾号00-09的用户用V2
- 观察1天，发现错误率升高
- 立即回滚到第1批（只有1%受影响）
- 修复问题后重新切流

第3批（20%）：尾号00-19的用户用V2
- 观察2天，一切正常

...逐步推进到100%

好处：出问题影响范围小，可以快速回滚
```

### 为什么是这个顺序？

**启动期先做架构基础（DDD+三表分离）**
- 代码结构和数据模型是根基，一开始就按工业级标准设计
- 后期改动成本极高，早期投入1天=后期投入1个月

**增长期再做业务功能（FIFO+规则引擎）**
- 初期业务简单，硬编码够用，过度设计是浪费
- 等业务复杂了，痛点明显了，再上高级功能

**成熟期再做性能优化（定期合并+离线计算）**
- 性能问题是"富贵病"，用户少的时候不会有
- 过早优化是万恶之源，先跑起来再说

**重构期再做保障机制（三重校验+灰度切流）**
- 这些是为系统升级服务的，平时不需要
- 只有在做大改动时才需要这些保险措施

  ### Q1：请介绍一下你的积分系统项目

  >
  > 代码层面实践了DDD，从贫血模型重构为充血模型，把业务行为封装到实体里。

  ### Q2：什么是三表分离？为什么要这样设计？

  **【逐字稿回答】**

  > 三表分离是指把积分数据拆成三张表存储：
  >
  > **第一是总额表**，只存用户当前有多少积分，带一个乐观锁版本号。用户查积分时直接读这张表，性能很好，也可以缓存。
  >
  > **第二是流水表**，记录每一笔积分变动，比如+100签到、-20消费。这张表只增不改，用于审计和对账。
  >
  > **第三是明细分桶表**，这是核心。每一笔入账是一个独立的Bucket，记录初始金额、当前余额、过期时间。消费时按过期时间排序，先扣快过期的。
  >
  > **为什么要这样设计？**
  > - 总额表读优化，查询快
  > - 流水表不可变，方便审计
  > - 明细表支持复杂的过期管理和FIFO扣减
  > - 三者可以互相校验，保证数据一致性

  ---

  ### Q3：FIFO扣减是怎么实现的？

  **【逐字稿回答】**

  > FIFO就是先进先出，优先扣除快过期的积分。
  >
  > 实现上，我查询明细分桶表时按expire_time升序排序，这样快过期的在前面。然后依次扣减：
  > - 如果第一个Bucket够扣，直接扣完
  > - 如果不够，扣完第一个，继续扣第二个，直到扣满为止
  >
  > 比如用户有3个Bucket：10积分2月15日过期、20积分2月20日过期。他要消费15积分，就先扣第一个Bucket的10分，再扣第二个的5分。
  >
  > 这样既符合"对用户最有利"的法律要求，也自然解决了积分过期的问题。

  ---

  ### Q4：如果连续签到3年，会产生1000多个Bucket，消费时不是要Update很多行吗？会不会死锁？

  **【逐字稿回答】**

  > 这是一个很好的问题，确实存在这个风险。
  >
  > 我的解决方案是引入**定期合并（Compaction）机制**。后台有个定时任务，扫描用户的Bucket，把同一用户、相同或相近过期时间的Bucket合并成一个。
  >
  > 比如用户有10个过期时间都在7天内的Bucket，合并成一个大的Bucket，金额是它们的总和。
  >
  > 这样就能控制Bucket数量，避免消费时需要Update太多行，也减少了锁冲突的概率。

  ---

  ### Q5：积分过期提醒怎么实现？5亿用户不可能扫全表吧？

  **【逐字稿回答】**

  > 对，扫全表肯定不行。我采用的是**T+1离线计算+MQ削峰**的方案。
  >
  > 具体来说：
  > - 每天凌晨用Hive或Spark计算未来7天即将过期的用户清单
  > - 把清单发到MQ，控制消费速率，比如每秒发5000条短信
  > - 这样既能及时提醒用户，又不会对系统造成压力
  >
  > 如果是中小规模系统，也可以用日历表方案，预生成未来30天的过期任务。

  ### Q6：退款时积分怎么返还？如果原积分已经过期了怎么办？

  **【逐字稿回答】**

  > 退款遵循**原路退回**原则。消费时我会记录扣减了哪些Bucket，退款时就往这些Bucket里加回去。
  >
  > 如果原积分已经过期了，有两种处理方式：
  > - 方案一：不退了，相当于积分过期了
  > - 方案二：延期退回，给7天的宽限期
  >
  > 具体用哪种看业务需求，我代码里两种都支持。

  ### Q7：为什么要用乐观锁？悲观锁不行吗？

  **【逐字稿回答】**

  > 乐观锁和悲观锁都可以，但积分系统的特点是**读多写少**，乐观锁更适合。
  >
  > 悲观锁是SELECT FOR UPDATE，会锁住记录，其他事务只能等待。如果并发高，会有很多线程阻塞，性能差。
  >
  > 乐观锁是用版本号，更新时检查版本号是否变化。如果没变就更新成功，变了就重试。这样读的时候不加锁，性能好。
  >
  > 积分查询很频繁，但扣减相对较少，所以乐观锁更合适。而且冲突时重试的成本也不高。

  ---

  ### Q8：DDD充血模型和贫血模型有什么区别？你为什么选择充血模型？

  **【逐字稿回答】**

  > **贫血模型**就是Entity只有getter/setter，业务逻辑全在Service层。这样导致一个业务操作要调很多Service方法，逻辑散落各处，难以维护。
  >
  > **充血模型**是把业务行为封装到Entity里，实体自己知道怎么验证自己、怎么计算。
  >
  > 比如我的Task实体有isValid()方法检查任务是否有效，有matchesUserTags()方法匹配用户标签，有calculateReward()方法计算奖励。
  >
  > 这样代码更内聚，也符合面向对象的思想。而且容易写单元测试，直接测实体的方法就行。
  >
  > 我选择充血模型是因为积分系统业务逻辑比较复杂，充血模型能让代码更清晰。

### 亮点1：DDD充血模型实践

**问题**：贫血模型导致业务逻辑散落在Service层，难以维护和复用

**解决方案**：
```java
// 充血模型：业务行为封装在实体中
```

## 四、面试常见问题

### Q1：为什么要从贫血模型改为充血模型？

**回答要点**：
1. 贫血模型导致业务逻辑散落在Service层，难以维护和复用
2. 充血模型将行为封装在实体中，符合面向对象设计原则
3. 实体自己知道如何验证自己，避免外部调用时遗漏校验
4. 代码可读性和可测试性显著提升

---

### Q2：如何保证数据迁移过程中的数据一致性？

**回答要点**：
1. **双写阶段**：新旧系统同时写入，确保数据同步
2. **三重校验**：
   - 明细实验表 vs 明细对照表
   - 新总值表 vs 老总值表
   - 新总值表 vs 新明细表
3. **自动修复**：发现不一致自动修复并循环验证
4. **全量校验**：切流前确保100%一致性

---

### Q3：灰度切流的实现原理是什么？

**回答要点**：
1. 基于配置中心动态调整灰度比例
2. 使用UID尾号进行流量分配（如尾号00-09对应10%流量）
3. 分批推进：1% → 10% → 20% → 50% → 100%
4. 支持快速回滚到上一稳定批次

---

### Q4：为什么选择MongoDB作为统一存储？

**回答要点**：
1. **扩展能力**：原生分片支持水平扩展
2. **并发能力**：支持高并发积分操作
3. **事务能力**：支持多文档事务
4. **灵活性**：文档模型适配多变的业务需求
5. **一致性**：支持majority写入确认

- 积分过期怎么办（定期合并、过期提醒）
- 退款怎么处理（原路退回）

这些都是**功能层面的设计**，回答的是"积分系统应该怎么做"。

这些都是**架构层面的演进**，回答的是"系统如何从A变成B"。
